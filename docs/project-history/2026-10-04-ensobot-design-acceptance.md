## 验收标准

依据用户最初反馈和已选方案，而不是依据“已有测试是否绿”：

1. 群聊不是用户逐个 @ 的单机问答：不点名先交主持人，成员能分工、互相补充/复核，主持人收口。
2. 像可观察的工作团队，而不是黑箱：用户能看懂谁在做什么、做了哪些操作、结果的依据在哪里。
3. 审批/问答是人能实际操作的流程；不靠切换到完全放行通过验证。
4. Bot 与工作台为同级窗口；刷新、关闭工作台、重启不应悄悄丢掉工作状态。

参见 [两轮实现记录](2026-09-30-ensobot-host-mode.md)。

## 环境与操作

- 新构建的真实 Electron / EnsoBot 页面，窗口 1100×760，独立临时 userData、独立空闲 CDP 端口。
- 页面驱动复用 `e2e/ensobot/cdp.ts`，用受信任的 `Input.*` 点击、输入、回车；不以 IPC 直接代替建群、发言、审批、群设置。
- 三位成员：林舟（主持人、协调者、inyx `claude-fable-5-1`）、小数（核算、inyx `gpt-6-astra`）、小审（独立复核、inyx `claude-fable-5-1`）。
- 两种协议为 Anthropic Messages / OpenAI Responses，三张卡均为 `supervised`；只按次允许，不用 `allowSession`。
- 隔离样例：三份文件 `orders.csv`、`policy.md`、`proposal.md`。CSV 重复了 A002，A003 的 14 元报价不符合首重/续重规则。错误方案合计 40，正确合计 28。
- 用户只发一条不带 @ 的审核需求；要求实际读资料、工具核算和独立复核，不规定成员应输出的具体对话。
- 之后通过私聊验证拒绝 → ask_user → 点击选项 → 允许；通过群设置换主持人、改上限，制造等待审批中的直接 @ 轮次与排队私聊，再杀进程重启。

| 不串私聊 | 群讨论结束时私聊 bot 气泡仍为 0 | 通过 |
| 当前状态可见 | 捕获排队、思考、工具、输出文字、等待审批；问答场景出现等待回答 | 通过 |
| 操作/结果可追溯 | 工作记录只给工具名与成败；参数大多为空，结果不可展开 | 未达标，见 F1/F2 |

## 未解决的问题

### F1 — 高优先级：流式参数摘要被冻结

这次群聊完成的 10 个工具步骤，9 个 `summary` 为空，另 1 个停在 `$rows = Import-Cs`。
真实工具结果确认它们读了具体文件、执行了完整命令；审批窗口也能展示完整命令，并非模型没提供参数。

`src/shared/ensobot/activity.ts:61` 的 `stepsFromAssistant` 遇到相同 toolCall id 直接跳过（第 69 行）。
流式首帧空参数/半参数先建了步骤，后续完整参数不会补写。两家模型均观察到。
结果是用户展开工作记录只能看到多个 `read`，连读取了哪个文件都看不清。

### F2 — 高优先级设计缺口：工作记录没有执行结果

`EnsobotWorkStep` 仅含 id/name/summary/status；`EnsobotWork.tsx:80` 的 StepList 只渲染这些字段。
展开后没有 stdout、错误详情或文件内容的查看入口（工作步骤内可点击按钮数为 0）。
本次核算确有输出，但只能去底层 session jsonl 验证；Bot 窗口仍主要依赖模型自己的文字复述。
“知道调用过工具”不等于“能核查工作结果”，与最初的非黑箱目标还有实质差距。

### F3 — 高优先级缺陷：直接 @ 的活轮重启后没有中断说明

复现：群里发 `@小数 ... Write-Output INTERRUPTED_AUDIT` → 等审批，不批准 → 发一条排队私聊 → 重启。
私聊正常续送，未批准命令没有成功 toolResult，权限没有被重放；但群里只剩原用户消息，之后无任何系统说明。

`ensobotHost.ts:1174` 的 `settleInterrupted` 只遍历 chain.waiting（主持人分派出去、等待回报的成员）。
人直接 @ / 初次唤醒主持人的链 `waiting` 是空数组；`loadRuntimes` 又先清掉 `active`，这一类活轮缺少恢复依据。
因此上一轮“重启时正在工作的成员都会写明中断”的表述过宽，当前只覆盖了部分分派分支。
修复必须保留不自动重放工具操作的安全边界，不能以自动再执行来遮掩缺失的提示。

### F4 — 体验差距：团队动态与等待状态还不统一

- “团队动态”入口实际 `setPage('members')`，是成员当前状态概览，不是此前设想的跨成员活动时间线。
- 两位成员都在等审批时，左下角正确显示“2 位成员在等你”，群列表却仍显示“2 位成员在工作”。
  群列表按 room activity 数量直接套用 working 文案，没有区分人工阻塞。
- 人工拒绝被工作步骤笼统标为红色“失败”，缺少“用户拒绝”的区分。
